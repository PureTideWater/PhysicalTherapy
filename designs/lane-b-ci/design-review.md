## 1. Findings

### R1 (blocking): F1 (a) lets release.yml restore build-branch caches into the binding capacity measurement, and F1 does not say so

- **Section:** §7 F1; §3.2 (ci-deps carries F1's documents); release.yml is not in any PR's file list.
- **Issue:** `release.yml`'s capacity job restores caches:
  - `actions/setup-node … cache: pnpm` (`release.yml:153-156`);
  - `actions/cache/restore` of `screening-scale-release-<hash>` (`:159-169`).

  It then measures the binding report that decision 13 attests. GitHub lets a tag run restore caches created on the
  default branch: "Workflow runs can restore caches created in either the current branch or the default branch"
  (github/docs `content/actions/reference/workflows-and-actions/dependency-caching.md:242-245`, fetched 2026-10-24).

  Today the default branch is `main` (`gh api repos/PureTideWater/PhysicalTherapy` gives `default_branch: main`), and
  `main` holds no workflow (`git ls-tree -r --name-only origin/main`: 11 files). So a tag run finds nothing to restore
  and builds the scale release in its own run.

  Under F1 (a), `claude/build-platform` becomes the default. Then:
  - Its push runs save `screening-scale-release-*` (`screening-capacity.yml:29-30` is the push trigger; the save at
    `:192-197` has no event condition).
  - ci.yml's new push runs seed the pnpm store and the new tsc and vitest caches.
  - The release's binding measurement would run on a scale release generated by another run.
  - That cache key hashes only `packages/synth/src/release/**`, `tools/release/scale.ts`, `packages/rules/src/**` and
    release 900001's directory, not the lockfile or the other code the generator imports. So a hit can serve a
    release built by different code.

  The F1 row's "What each gives up" omits all of this. So does the task's check "caches cannot carry state into
  release.yml".
- **Fix:**
  - In ci-deps, whatever F1's answer: `release.yml` builds the scale release in-run (drop the restore step), and
    `setup-node` runs with no `cache:`.
  - Add a `workflows.test.ts` rule: release.yml uses no `actions/cache*`, no `setup-node` `cache`, and no buildx
    `cache-from`.
  - Add to F1 (a)'s give-ups: every branch's runs and every tag's run can restore the build branch's caches, and
    release.yml is made cache-free so the attested report depends only on its own run.

### R3 (should_fix): the shard-union acceptance command does not shard

- **Section:** A2 ("`vitest list --project db --shard=k/4 --filesOnly` for k = 1..4: disjoint, and their union equals …");
  §3.1.7 step 5; CI-04.
- **Evidence:** in the worktree, `pnpm -s vitest list --project db --shard=$k/4 --filesOnly` for k = 1..4 printed 105
  files each time, the same as the unsharded list (vitest 5.0.4). `list` ignores `--shard`. A verifier would see
  "not disjoint" (a false failure). A union-only check would pass whatever the split.
- **Fix:**
  - Each `db (k/N)` job prints the files it ran to its log, from vitest's json reporter
    (`jq -r '.testResults[].name' | sort`), with their count and SHA-256. The verifier takes the union of the N logs
    with `get_job_logs`.
  - CI-04's unit test computes the split through vitest's own sequencer: its Node API with `shard: 'k/N'`, then
    `sequencer.shard()` over the db project's files. It asserts disjointness and the union for both N = 4 and N = 6.
  - Remove the `vitest list` command.

### R5 (should_fix): the mutation "affected" rule misses upstream workspace packages, fixtures and lockfile scope

- **Section:** §3.4.1 `changes` row ("A package is affected by its own directory. Money affects all four; pricing affects
  packets. Shared inputs …").
- **Evidence:**
  - `packages/pricing/package.json` depends on `@tp/contracts`, `@tp/money` and `@tp/rules`.
  - `packages/packets/package.json` depends on `@tp/money`, `@tp/pricing` and `@tp/triage`.
  - `packages/ledger/package.json` depends on `@tp/db` and `@tp/money`.
  - So a PR that changes `packages/rules/src` (watched and frequently changed), `packages/triage` or `packages/db`
    can let pricing's, packets' or ledger's mutants survive, and its PR run would not measure them.
  - [S2] §6 listed "the fixtures the tests read". The design dropped it.
  - The gap shows up only on the post-merge push run, which turns the build branch red after the merge.
  - The same rule makes every lockfile change ("the lockfile gives all") a full 6-shard run. That includes every
    Dependabot npm PR (see R23).
- **Fix:** `affected.ts` derives each package's closure:
  - the transitive `workspace:*` dependencies from the `package.json` files;
  - its test set's import graph (traced as `tools/screening-capacity/watched.ts` does);
  - the fixture paths those tests read.

  A lockfile diff affects a package only when it changes a resolved version in that closure, or in the test tooling
  (vitest, @stryker-mutator/*, fast-check). Add table cases for rules → pricing and packets, triage → packets,
  db → ledger, and a Dependabot `@aws-sdk` lockfile bump → none.

### R18 (should_fix): the lint scheduler's arithmetic fails on a private runner, which audit #109 names

- **Section:** §3.1.2 "Lint".
- **Evidence:**
  - The heaps are 6,144 + 4,096 + 4,096 = 14,336 MB.
  - Public runners have 4 vCPU and 16 GB. Private standard runners have 2 vCPU and **8 GB**, not 7 (github/docs
    `data/reusables/actions/supported-github-runners.md:115-116`).
  - Under the stated rule (heaps within `os.totalmem()` − 2 GiB), a 16 GB host (about 15.6 GiB reported) admits two
    groups, not three.
  - On 8 GB (about 5.7 GiB of budget) the web group's 6,144 MB is never admitted, so it waits forever or the rule is
    ignored. Audit #109's problem is exactly "a private repository's … runner cannot hold" lint.
- **Fix:**
  - Each group's heap is the smaller of its heap and the budget, and at least one group always runs.
  - `groups.test.ts` plans for 16 GiB and 8 GiB.
  - Correct "7 GB" throughout. The measured web peak of 4,813 MB fits.
