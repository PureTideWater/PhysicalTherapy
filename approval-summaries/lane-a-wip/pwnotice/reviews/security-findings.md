### SEC-01 blocking D10's ground for "Every session of this account has ended." fails for a sign-in step begun before the reset; D10 makes this review's answer a gate before the pull request opens
- Where: docs/adr/0091-tell-an-accounts-address-…md:157-172 (D10, N-3), :290 (option (b)'s switch), :349-350 (Revisit when); apps/web/src/lib/auth/sign-in.ts:291-314 (`authenticated()` opens the session; nothing compares the step with a reset), :414-419 (`answerTotp`), :440-459 (key registration), :547-551 (the provider sign-out's failure is logged and not counted); apps/web/src/lib/auth/sessions.ts:47-91; docs/product/test-matrix.md, SGN-16's row; fixtures/synthetic/SGN-16/expected.json:5.
- Defect: D10 closes #125's N-3 with option (a) on this sentence: "a provider session that survives a failed `AdminUserGlobalSignOut` can only finish, within those minutes and through the app's server, a sign-in step already started, and cannot reach a page, PHI or a setting", and leaves to this review "whether a step begun before the reset can finish into a session after it: if it can, this decision says so and SGN-16 gains the case; if a surviving provider session can do more than finish a sign-in that already proved both factors, the build switches to option (b) before the pull request opens". It can, in two ways, and the sentence is wrong for both:
  - (a) A step that proved the old password before the reset and waits at the second factor opens a session when the code is entered after the reset. It does not depend on the provider's sign-out. That sign-in had proved one factor, the password the reset was meant to end, not both.
  - (b) A key-registration step (password and code proved before the reset; the provider's grant sealed in the step for 15 minutes) registers a hardware key after the reset when the provider's sign-out had no effect, and that key then signs in with no password: a factor the reset does not remove.
  Nothing in the app ties a step to the account's latest reset, and `security event: password reset provider sign-out failed` is logged at error and counted by no filter, so in case (b) nobody is paged.
- Failure: a person resets because someone else knows the password and can read the authenticator (a shared device, a copied seed). The email tells them "Every session of this account has ended." Within the step's 3 minutes (step-limits.ts:12) the other party's waiting step opens a 12-hour session with a current code. Or, on an account that must use a hardware key and has none yet, when `AdminUserGlobalSignOut` failed, the other party registers their own key within 15 minutes (step-limits.ts:14-17) and keeps a way in that no later reset ends. For that reader the line was false, and SGN-16 has no case that says so.
- Evidence:
  - (a) `exp1_step_after_reset.ts` (out_exp1_step_after_reset.txt): `flow.start(email, OLD)` gives `pending mfa`; the reset answers `{"kind":"reset"}`, one notice is `pending`, open sessions 0, the old password is refused; then `flow.answerTotp(<the step begun before>, <a current code>)` answers `signed_in`, the session resolves `active`, and `sessions of the account: [{"opened_after_change":true,"open":true}]`.
  - (b) `exp10_grant_after_reset.ts` (out_exp10_grant_after_reset.txt): `pending register_key` before the reset; after it `completeKeyRegistration` answers `{"kind":"key_registered"}`, `beginKey`/`completeKey` answer `signed_in`, session `active`; the audit trail reads `password_reset_requested, password_reset_completed, hardware_key_registered, sign_in`. The twin's `globalSignOut()` does nothing (dev-provider.ts:393-395), so this is the case of a sign-out that failed.
  - At Cognito: unproven (no pool in this lane). What would prove it, on staging with a synthetic account: (a) start a sign-in, complete a reset in another browser, answer the first browser's code step inside 3 minutes; (b) with an access token issued before `AdminUserGlobalSignOut`, call `StartWebAuthnRegistration` (it should be refused when the sign-out succeeded). ADR 0081:288-289 already records (a) as true of Cognito ("can still open an app session after the revoke"), which D10 does not carry.
  - `grep -n "begun before\|before the reset" apps/web/src/lib/auth/sign-in.db.test.ts`: no case. `grep -rn "provider sign-out failed" infra docs`: nothing counts or names the line.
- Fix: the least D10's own rule asks, before the pull request opens: (1) D10 says both cases in place of the sentence quoted above, and "Revisit when" :349-350 becomes a statement of fact that points at the close; (2) SGN-16 gains two cases in sign-in.db.test.ts, written from exp1 and exp10 (they pass today: they record what a step begun before a reset can do, and that the notice says the same lines); (3) `security event: password reset provider sign-out failed` joins `RESET_AND_ENROLMENT_COUNTS` with an alarm and a runbook step, infra only, as D15 did for the other line (monitoring.test.ts's literal list of eight counted lines fails until it is nine), so a reset whose provider sign-out failed pages whichever line the email carries; (4) a ruling on option (b): for (b)'s case its narrower line is the honest one; for (a) it changes nothing, since (a) does not depend on the sign-out. The close for both, which is the web's and so not this pull request's as scoped: refuse to open a session or register a key from a step whose challenge was issued before the account's latest completed reset. The step's own sealed `startedAt` (pending.ts:26) against the reset event's time needs no fact about Cognito's `auth_time`, which is what holds SEC-N5 back in Schema PR 6; its test, "a step begun before a reset opens no session after it", fails today.
- Needs: a founder decision (S2's ruling for option (a) rested on the facts this review was asked to test; it is S2's or the founder's to repeat or change), then ADR, matrix, test and infra edits; no migration change.
