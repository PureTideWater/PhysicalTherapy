# Review (2): database, mail and deploy. The password-changed notice at f8560588

No blocking finding. Five to fix (DB-01 to DB-05), six notes (DB-06 to DB-11).

How it was checked: everything below was run on scratch databases on port 5433, with the worktree's own modules imported by path. `tp_rev_db_1` was a copy of `tp_pwn_tpl`. `tp_rev_db_2` was the base, migrated by the worktree's own runner from `git archive refs/review/pwn-base packages/db/migrations`, then seeded with 50 users, 200,000 audit events and 500,000 mail records, all synthetic. `tp_rev_db_3` to `_5` were copies of it. ### DB-01 should fix The mail_events job writes PASSWORD_NOTICE_UNDELIVERED only after the queue's delete, so a failed delete loses the page for good
- Where: `apps/worker/src/platform/mail-events.ts:453` (the delete) and `:471-489` (the lines) at f8560588.
- Defect: the record commits inside `recordEvent`; the message is then deleted from the queue (`:453`); only after that are the lines for what the record returned written. The seventh column is returned by the one call that reported the notice (migration `:513-515`), so a run that ends between the commit and the line never writes it, and the same event received again is answered `recorded = false` with every column null.
- Failure: SQS's delete fails after a bounce's record has committed (or the task is stopped there). The notice is `undelivered`, `password_notice_undelivered` is in the audit log, and no `PASSWORD_NOTICE_UNDELIVERED` line exists. The alarm never rises and nobody tells the person another way, which ADR 0091 D9 promises for every such notice.
- Evidence: `REV_DB=tp_rev_db_1 pnpm -s exec tsx $S/lost-page.mts` (the worktree's `sendPasswordNotices` and `runMailEvents`; a queue whose delete rejects once, after the bounce's record). Printed: `first mail_events run threw: synthetic: the queue could not delete the message`; second run `recorded: 0, repeated: 1`; `notice: { state: 'undelivered', reported: true }`; `audit: [ { action: 'password_notice_undelivered', request_id: 'rev-events-1' } ]`; `lines with PASSWORD_NOTICE_UNDELIVERED: 0` (`evidence/lost-page.out`).
- Fix: delete the message last. Write the lines the record returned (`:459-492`) before `source.remove`, so an event received again still logs nothing and one whose delete failed has already paged. The three older columns' lines sit in the same place and get the same move. The test that fails before it: in `mail-events.db.test.ts`, the new case's bounce through a source whose `remove` rejects once; expect one `PASSWORD_NOTICE_UNDELIVERED` line over the two runs (today none).
- Needs: nothing

### DB-02 should fix A notice whose record fails after SES accepted its message is sent again on every run, uncounted, until the 24-hour cutoff, and every notice behind it waits
- Where: `apps/worker/src/platform/password-notices.ts:140-144` (the rethrow) and `:168-169` (the run ends at the first throw); migration `:347-355` (`attempts` moves only in `operator_password_notice_failed`); `docs/adr/0091-*.md:310-311` ("the person may get two copies").
- Defect: an error after SES accepted a message (the record's refusal, or its COMMIT) is rethrown with nothing recorded. The notice stays pending with `attempts` and `next_attempt_at` unchanged, so it is first in the next run's due order again. The rethrow ends the run, so the notices after it are not tried. Only the 24-hour cutoff ends it.
- Failure: while the record keeps failing for one notice, its account is sent one more "Your password was changed" on every run (the schedule's minute and pg-boss's two retries of each failed job: over a thousand in 24 hours), and no other account's notice is sent; at 24 hours they fail as stale. A failure that happens once costs one extra copy, as the ADR says. The one input found that repeats it today is a message ID outside `^[A-Za-z0-9-]{20,100}$`, which `operator_password_notice_sent()` refuses (23514) after SES has accepted the message. Nothing SES sends today has that shape, so this guards the next change (SES's ID, or a later edit of the record path); it is not an outage now.
- Evidence: `tsx $S/resend.mts` (a sender that delivers each message and returns an ID the record refuses): six runs, each `23514 a password notice is recorded with the message ID SES gave`; `messages SES accepted for the one notice: 6 | to one address: 1`; `notice: { state: 'pending', attempts: 0, due: true }`. `tsx $S/head-of-line.mts`: `6 runs, 6 failed: the first account was sent 6 messages; the second account, behind it, 0`.
- Fix: count that try. In `send()`'s catch, when a message was accepted and the error is not a refused send, record it in a new transaction with `operator_password_notice_failed(notice, 'RecordFailed', false, request)`, then rethrow. The notice backs off 1, 5, 15 and 60 minutes and fails, reported, at the fifth try (five copies at most). It leaves the head of the due order, so the next run sends the others. The job still fails, so the failed-job alarm still tells the operator. ADR 0091's residue then says "one more copy for each run whose record fails". The test that fails before it (`password-notices.db.test.ts`): a sender whose ID the record refuses and a second notice behind it; after one run `attempts` is 1 and the notice is not due, and the next run sends the second.
- Needs: nothing

### DB-03 should fix The header, ADR 0091 D11 and the runbook say requests "wait and then proceed" under the locks; since #137 a signed-in request is refused as busy after three seconds, and "audited mutation" leaves out audited reads
- Where: migration `:47-50`; `docs/adr/0091-*.md:184-187` and `:312-313`; `docs/runbooks/deploy-and-rollback.md:347-349`.
- Defect: all three say that, once the locks are held, every write of `"user"`, "every audited mutation", every read of `audit_event` and every read or write of `mail_send` waits and then proceeds. Since #137 every signed-in request's transaction carries a three-second lock timeout (`apps/web/src/lib/http/invoke.ts:103`, `:341-346`): past it the request is rolled back and answered busy. An audited read writes `audit_event` too (`readWithAudit`, `packages/db/src/authz/audit.ts:49`, in 20 web modules), so nearly every signed-in page waits on that lock, not only mutations.
- Failure: with the locks held past three seconds a signed-in person's page shows its error state and a form answers "The records this form needs are being updated, so nothing was saved." (`busy-words.ts:16`), while sign-in, which has no timeout, waits and proceeds. The window measured here is 0.2 s, so at today's sizes nobody is refused. The sentence is wrong in a file that cannot be edited once applied, and in the operator's runbook.
- Evidence: `tsx $S/loop.mts`, last block, the migration's own loop holding its locks for 4 s (`evidence/loop.out`): `web audited mutation: refused 55P03 after 3003 ms`; `web settings save: refused 55P03 after 3003 ms`; `web console mail page: refused 55P03 after 3002 ms`; `web page reading a user (no write): proceeded after 4 ms`; `sign-in bookkeeping (no lock_timeout): proceeded after 3998 ms`. The window: `psql -d <copy of tp_rev_db_2> -f $S/locks-at-end.sql`: `ALTER TABLE` 199.5 and 229.7 ms over 500,000 mail records (125 MB), every other statement under 8 ms; the runner's whole run of the file 286 ms.
- Fix: say it in the three places: jobs and sign-ins wait and proceed; a signed-in request waits up to its three-second lock timeout and is then refused as busy with nothing saved (ADR 0092's amendment); every audited read as well as every audited mutation; the measured window. While the header is open: "Rollout: migrate, then the new platform image …, then the rest" (`:61-62`) names an order the stack does not have (every service depends on the migration run alone, `infra/lib/constructs/compute.ts:429-431`); nothing needs one. Words only, so no test.
- Needs: a migration change (its header only). Appendix D of the domain model carries the file's SHA-256, so the document is regenerated and its approval hash changes: before the founder is asked, not after.

### DB-04 should fix The lock-loop test passes on a loop that keeps "user" and audit_event locked while it waits for mail_send
- Where: `packages/db/src/password-notice.db.test.ts:1118-1133`.
- Defect: after each holder ends, `waitFor(migrationPid, PgSleep)` returns at once, in the sleep that began before the holder ended, so the `signIn()` after it (`:1121`, `:1124`, `:1127`) runs before the loop has tried again. The third is the only one that could meet a try that took `"user"` and `audit_event` and was refused `mail_send`, and it runs before that try. The loop is copied from migration to migration (ADR 0083's pattern), so this test is what guards the next copy. The loop as written is sound (see "Checked, sound").

The migration's own loop at the same point: `locks it held mid-loop: []` (`evidence/loop.out`).
- Fix: after `userHolder` commits, wait for a new try (the backend leaves `PgSleep` and enters it again), assert `pg_locks` has no granted lock of that backend on the three tables, then the sign-in. The mutant then fails.
- Needs: nothing
