### F1 [should-fix] Acceptance is not bound to the diff the person reviewed: a stale page accepts a change nobody saw
- **Where:** `apps/web/src/lib/routes/pricing.ts`:331
- **Evidence:** The accept route's input is only `z.object({ runId: opaqueId })` (pricing.ts:331). The two Accept forms post only practiceId and runId ([runId]/page.tsx:207-212; compare/page.tsx:119-123). In its 'acceptable' branch, acceptRun (apps/worker/src/price/rerun.ts:312-330) uses block.replacesId, but only to choose the page's diff base; it never compares it with what the client saw. The compare route's doc says 'J17: the diff a person accepts is the change accepting makes' (pricing.ts:211). Nothing enforces that at accept time.

Failing sequence (the PRC-26 shape, reruns-routes.db.test.ts:483-499):
1. Run N is in effect for February. Re-runs `one` and `two` of N are created and priced, `one` first.
2. Manager A opens `two`'s page. rerunAcceptance says acceptable with replaces N, and A reviews the diff of `two` against N.
3. Manager B accepts `one`. `one` does not supersede `two`: it was priced earlier, under the same release, with the same cut-off. So `two` stays acceptable, now with replaces = `one`.
4. A clicks Accept on the page loaded in step 2. B's commit happened before A's transaction began, so TOOK_EFFECT_MEANWHILE is false. No refusal fires, so refreshOnError never runs. The acceptance succeeds.

Result: `two` replaces `one`, and A never reviewed the diff of `two` against `one`. Every line where `one` differs from N changes without anyone seeing it. The PR's own test accepts `two` with no base at line 499, which shows the input cannot carry one.
- **Fix proposed:** Have the Accept forms post the run the shown diff was against: `replacesRunId`, set to acceptance.replaces.id on the run page and to before.id on the compare page. Add it to the route's Zod input and to AcceptRunInput. In acceptRun, after rerunBlock returns 'acceptable', refuse with RerunRefusedError('changed_meanwhile', ...) when block.replacesId differs from it. That message already tells the person to check the page again, and refreshOnError then shows the current diff. An acceptance already recorded stays idempotent whatever replacesRunId says. Add a db test of the sequence above: after `one` is accepted, an accept of `two` naming replacesRunId = N is refused and records no pricing_run_accepted event, and naming `one` succeeds.

### F1 [should-fix] completed_at is stamped before the execution lock, so the order of completed_at is not the order runs read their inputs; the ADR wrongly says the window is closed for first runs
- **Where:** `apps/worker/src/price/execute.ts`:251
- **Evidence:** execute.ts:251 opens priceRun's transaction, and its now() becomes completed_at (execute.ts:297; the trigger requires it, 20261105090000:599-601). The execution lock comes later, at execute.ts:253. Between the two, withJobScope runs two round trips: set_config, then app_actor_is_person() (packages/db/src/authz/scope.ts:259-283). in-effect.ts NEWER_PRICING and ADR 0037's amendment say 'completed_at order is the order in which they read them', and the ADR says 'For a first run X the window is closed'. That argument, like design review finding 6, assumes R is created after X starts running. Failing sequence: Q (Jan-Mar) is in effect, and a person creates R, a re-run of Q (createRerun passes; nothing is pending). The monitor then creates X, a Feb first run; createPricingRun does not check for a queued re-run. A mapping correction is about to commit. Two worker executions pick up both jobs at about the same moment. X's priceRun issues BEGIN at time a, and R's at time b > a. R reaches the lock statement first, reads mappings and settings, and commits minutes later. The mapping correction commits. X takes the lock and reads the corrected mapping. Result: R.completed_at = b > X.completed_at = a. At acceptance, NEWER_PRICING(X,R) is false, the release is the same, and the cut-off clause does not apply (different period), so R is accepted. It ranks after X, and every Feb line the two share moves from X's corrected pricing back to R's older pricing, which is the regression this PR exists to prevent. The model (rerun-model.ts:286-300) stamps completedAt and reads lines in one atomic tick, so it cannot show this. Exposure today: production runs one worker task (infra/lib/environments.ts:111), and price jobs use batchSize 1 with localConcurrency 1. So this needs two executions at once, for example during a rolling deploy's overlap or after scaling out. execute.ts:252 ('One run of the practice at a time, whatever the queue does') already plans for concurrency. The same mistake narrows the ADR's 'residual window' for an X that is a re-run: R only has to be picked up in the gap, not created in it.
- **Fix proposed:** Make the stamp follow the lock, with no migration. Take the execution lock before the transaction that stamps completed_at begins: a session-level pg_advisory_lock on the pricing connection before BEGIN, released in finally. Alternatively, have the job's transaction helper take the lock before anything else, so now() begins after the lock is granted. Then completed_at order equals read order, and the ADR's claim holds for first runs and re-runs alike. Model the gap in rerun-model.ts (split startPricing into a begin-stamp step and a read step) so the property test covers it. Correct the ADR's residual-window paragraph either way.

### F2 [should-fix] NEWER_PRICING ignores the place-of-service split (and triage date) fixed at creation, so an older-split re-run is accepted over a newer-split run
- **Where:** `apps/worker/src/price/in-effect.ts`:63
- **Evidence:** Every run fixes place_of_service_split_id when it is created (20261105090000:565-570), and execution prices with that split (settings.ts:35, pricing_run_split(run)), exactly as it fixes release_no. The engine's as_of (the triage date for windows) is also fixed at creation: runAsOf(run.created_at), execute.ts:225,275. NEWER_PRICING (in-effect.ts:63-64) gives that treatment only to release_no and judges everything else by completed_at. Failing sequence: Q (Jan-Mar) is in effect under split S1. R, a re-run of Q, is created and fixes S1. A contract specialist approves split S2 (console_approve_place_of_service_split, which becomes the split in force). The monitor creates X, a Feb first run, which fixes S2. X is priced before R (R's job is retrying, or two workers). R is then priced, still under S1. At acceptance, X.completed_at < R.completed_at, the release is the same and the period differs, so SUPERSEDES_RERUN is false and R is accepted. The Feb lines X and R share move from S2 (facility or non-facility) to the superseded S1, and their expected amounts change with no newer input behind it. The model has no split (rerun-model.ts:25-40). Its regression invariant (rerun-model.ts:412) reuses the rule's own completedAt/release idea of 'newer', so the property test cannot catch a fixed input the rule leaves out.
- **Fix proposed:** Add the split to NEWER_PRICING in the same form as the release: X is newer when its split's approved_at is later than R's (join place_of_service_split, comparing (approved_at, id) as place_of_service_split_in_force() orders them). Decide on the creation-day triage date explicitly as well, and either include it or record why it is safe in the ADR. Add the split to the model, ideally as a general 'inputs fixed at creation' vector so the regression invariant is not defined by the rule under test. Add a db test where X has the later split, was priced earlier, and R is refused.

### F3 [should-fix] The SQL's cut-off clause and later-release clause are untested: disabling either leaves every db test green
- **Where:** `apps/worker/src/price/rerun.db.test.ts`:617
- **Evidence:** Mutation runs in a scratch worktree at 961783a, with DATABASE_URL on PG18 port 5433, running vitest --project db on rerun.db.test.ts and reruns-routes.db.test.ts. (a) Replacing SUPERSEDES_RERUN's '(SAME_PERIOD AND CUT_OFF(x) > CUT_OFF(rr))' with false: 33 of 33 pass. (b) Replacing NEWER_PRICING's '(x.release_no > r.release_no AND NOT withdrawn)' with false: 33 of 33 pass. The cut-off clause is the only protection for Sequence A when the newer run X of the month was priced before R (design §2.1: 'Sequence A, even when X was priced before R'). In every db sequence (tie A, PRC-25, PRC-26) X is executed after R, so completed_at alone decides. No db test has an overlapping X under a later, non-withdrawn release that was priced before R. PRC-26 under 900004 is also priced later. rerun-rule.property.test.ts checks only the TypeScript model's copy of the rule (rerun-model.ts:141-154), and the tie at rerun.db.test.ts:617-749 is three hand-built sequences, so neither reaches these SQL branches.
- **Fix proposed:** Add db cases, with matching tie sequences, that make each clause decide alone. (1) Same period: create X, a first run of February, after a late line loads; price X; then price an R that was created earlier (queue both, execute X first). Expect superseded with the late line still in effect. (2) Create R under release N, publish N+1, create and price an overlapping X under N+1, then price R. Expect superseded. Better still, drive the tie from fast-check sequences against the DB (a small numRuns), so the SQL rather than only its transcription is property-tested.

### F4 [should-fix] Under overlapping periods the diff a person accepts against is not the change accepting makes (J17)
- **Where:** `apps/web/src/lib/routes/pricing.ts`:166
- **Evidence:** The diff's base is the exact-period run in effect, rerunBlock's replacesId (rerun.ts:145-146,177; pricing.ts:164-176). The compare page offers Accept only against that run (pricing.ts:238-248). But a line's pricing in effect is PRICED_IN_EFFECT over runs of any period (in-effect.ts:38-43), and accepting R moves every line R shares with an other-period run X that is not newer (since(X) > since(Q)) from X to R. Sequence: Q (Jan-Mar) is priced under mapping M1. The mapping is corrected to M2. The monitor prices X (Feb, a late line) under M2. A person re-runs Q to get R (M2, priced after X, so acceptable). R's page diffs R against Q and lists every Feb line as changed by the mapping. Those lines already read X under M2, so accepting changes nothing on them. Conversely, if settings changed between X and R and R equals Q on some lines, those lines change on acceptance (X to R) and are not listed. ADR 0037's amendment, under 'The diff base', admits this and argues the moves are to newer pricing. J17 requires the re-run to list 'exactly which lines would change before anyone accepts it', and §2.4 of the design claims the page 'shows the diff against the pricing the acceptance would replace'.
- **Fix proposed:** Diff R against each line's current pricing in effect: a compareRuns variant in diff.ts (apps/worker, not under packages/pricing) whose before-side is PRICED_IN_EFFECT restricted to R's period. Or, at least, name the other-period runs whose lines R would take over and show their diffs too. Then the screen and the ADR can claim exactness.

### F5 [nit] 'There is nothing more to accept' (and the hidden Re-run offer) relies on rerunReasons, which cannot see settings, location or live-fact changes
- **Where:** `apps/web/src/components/pricing/display.tsx`:202
- **Evidence:** A superseded re-run's page says the newer run 'already prices these lines under rule release N and the mappings and contract versions in force now. There is nothing more to accept.' It also hides the Re-run form (page.tsx SupersededRerunOffer: same_period && target.rerun.length === 0). The decision rests on rerunReasons (rerun.ts:42-52), which checks only mappings, versions, release and withdrawal against the run's created_at. Case: X (same period, later cut-off) was priced before R, superseding R by cut-off alone. Between X and R the practice's ZIP+4 or default rounding changed (settings.ts:30-37), so R carries newer settings than X. rerunReasons(X) is empty, so the page says there is nothing more to accept and offers no re-run, although R does hold newer pricing on those lines and so would a re-run of X.
- **Fix proposed:** Show 'nothing more to accept' only when the superseding run was priced after R (X.completed_at >= R.completed_at, the newer-pricing branch) and rerunReasons is empty. When R was superseded by cut-off alone, always offer the Re-run of the run in effect.
