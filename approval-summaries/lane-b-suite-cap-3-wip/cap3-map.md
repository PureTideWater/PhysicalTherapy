### claimLines (remittances.ts:249) in detail (shared: pass x3 chainContext + per candidate x2, manual, web, report)
SQL: WITH RECURSIVE named: step `JOIN claim k ON k.superseded_by_claim_id = n.id` (254) and per OUTPUT ROW the correlated `(SELECT k.id FROM claim k WHERE k.superseded_by_claim_id = s.claim_id ORDER BY k.created_at DESC, k.id LIMIT 1)` (259). The two adjustment subqueries (257-258) use adjustment_by_line: fine.

## 3. Advisory locks per pass transaction (base)
lockLedger 'ledger:'||practice: 1. ledger_entry_within_line 'ledger_line:'||line: 1 per distinct line with an approved/posted/deposited entry (or correction of one) written. ledger_entry_within_evidence 'ledger_evidence:'||row: 1 per posting/EFT row with a posted/deposited entry. line_status_rules 'line_status:'||line: 1 per line with a stage event. submission/payer_response_belongs 'submission:'||case: per case with a no-change response. => ~3 per line (CAS-42.3 says so), O(N) per transaction => 53200 on a default cluster (max_locks_per_transaction 64). ## 5. Order constraints (what a fix must keep byte for byte)
- ledger_entry.seq order: ledgerEntries orders by seq; ledger_line_stage compares max(seq) of approval/proof/recoupment; insert entries in the same order (line by line, candidate by candidate).
- ledger_match: on the base CHAIN_ORDER sorts by data (matched_at = txn time, kind, bpr16, created_at, position, id), so cross-line insertion order is free; AFTER the interest fix, CHAIN_ORDER and ledgerMatches are ORDER BY m.seq = insertion order, so batching must insert matches in exactly today's order (per line in caseLines order, candidates in chainOrdered order; then reversals, WOs, L6s, postings, deposits).
- Baselines are carried per line through the pass (matchCandidate 772): a line's candidates must still be compared in chain order with state carried; lines are independent of each other in step 1 (each reads only its own chain + its own ledger), which is what makes a set-based candidate search per pass possible.
- line_status: per line, payer_approved before recovered; refresh_cases is statement-level, so a multi-row INSERT refreshes each case once per statement (BEFORE ROW triggers see earlier rows of the same statement; keep the two-stage jump in two statements or ordered rows).
