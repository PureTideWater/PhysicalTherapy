- **optional**, `apps/worker/src/report/content.ts:830`: The arena is not released when gatherReport throws after the line loop. gatherReport releases the arena in its catch only around the cursor loop (lines 797-828). - **optional**, `apps/worker/src/report/generate.ts:88`: If the PDF render fails, a sealed CSV object is left behind with nothing pointing to it. The head now writes the sealed line CSV (documents.write under a fresh random csvKey) before services.pdf.render runs. On the base, the render ran before either write, so a Chromium failure stored nothing. Now each failed render leaves one sealed CSV object of line-level PHI. Rolling back the transaction does not remove it, and no audit_report row points to it, so up to three can pile up per report across its retries. Before, the only way to leave an orphan was a failed CSV write after the PDF was stored, and that object was the PDF. I found this by reading the code: the write at generate.ts:88 runs before the render at :93, and the code holds no orphan sweep (searched apps/worker/src for 'orphan'). Design 5.3 point 4 chose this order on purpose so the arena is released before Chromium prints, and no figure or byte changes. This is about how long stored objects live, not about correctness. Fix: Either accept it and note it in ADR 0083, or delete csvKey in a catch around auditReconciliation, the render and the PDF write when any of them throws. The delete needs to be allowed for an object written under this attempt's own key.
