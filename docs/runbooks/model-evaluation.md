# Model evaluation: the real-model baseline, re-baselining and serving a feature

Trigger: before milestone 10 closes (the first real-model baseline); before a prompt version or a model change reaches
users; when the evaluation set changes (a new case, a truth fix, or a pdf.js or Textract-reader bump that changes the
pages as read). The decision is docs/adr/0070 (Parts 1 and 2), amending ADRs 0051, 0052 and 0054.

**People only.** Every step here that calls a real model is run by a person with model access: the founder, or the
person he names. No build session, agent or CI job runs it: the build has no model credentials, and CI only ever runs
the local deterministic provider, which proves the path and the gate, not a model. Models are named here by their role
only (the contract model, the larger model the contract prompt pins for contracts a specialist marks ambiguous, the
narrative model); their identifiers are configuration, pinned in each prompt version's `prompt.json`.

## What a feature needs before production serves it

A real provider serves a model feature in production only when all of these hold for that purpose and, for contract
proposals, that variant (`servingDecisions`, `packages/model-gateway/src/evaluated.ts`). Anything missing turns that
feature off on its own, with hand entry on its screen; when nothing is served, the configuration is refused as before.

| Reason it is off | What clears it |
| --- | --- |
| `no_set` | Nothing yet: evidence requests and the denial-letter reader have no synthetic set, so they stay off in production (ADR 0070, P5) |
| `no_entry` | A recorded entry in `eval/baseline.json` for the current prompt version, its content hash, the provider, the model and the variant (steps 2 to 4) |
| `floor_unset` | Every recall and precision floor of `eval/floors.json` set (step 1) |
| `below_floor` | The entry's counts meeting every floor. A floor raised after recording turns the feature off until a new record meets it |
| `price_unconfirmed` | Each model the variant pins confirmed in `config/models.json` |
| `permitted_pending` | The permitted run's record in the entry (steps 6 and 7); until then the feature is evaluable only |

## 1. The floors come first

The per-field recall and precision floors for contract proposals are the founder's, set with the contract specialist
(ADR 0070, F1). `eval/floors.json` ships with every floor `null`, and while any is `null` the gate refuses to record a
real provider (`floor_unset`) and production does not serve it. Before the first real-model run, a pull request sets
them, quoting the founder's ruling in its description; a floor is decimal text with at most six places in [0, 1]
(`"0.95"`), held over the whole of set v2. Nobody else chooses the numbers, and no run is made first to fit them to.

The local provider is never held to floors. Every provider is held to the local reference on the unfaithful cases;
the CLI runs that reference itself (a handful of local calls) before it gates, so nobody supplies it. If it cannot
(a run of another set or prompt), the gate reports `reference_missing` with the cases it could not cover, and blocks.

## 2. The run

From a checkout of the commit being evaluated, on a machine with no real data (the sets are synthetic and every call
names no practice, so the gateway lets them reach a real provider outside production):

```sh
pnpm install --frozen-lockfile
MODEL_PROVIDER=bedrock AWS_REGION=<region> pnpm --filter @tp/model-gateway eval --provider configured --report eval-default.json
MODEL_PROVIDER=bedrock AWS_REGION=<region> pnpm --filter @tp/model-gateway eval --provider configured --variant ambiguous --only contracts --report eval-ambiguous.json
```

(`MODEL_PROVIDER=anthropic` with `ANTHROPIC_API_KEY` for the alternative path.) With `OPERATOR_DATABASE_URL` set, each
call is logged in `model_call` as an evaluation call (the operator role, no practice). The large tier
(`fixtures/synthetic/MOD-09/generated/`) is written before the run and checked against its pinned hashes; nothing
needs to be generated by hand.

**Cost.** Set v2 is 63 documents, about 500 pages, at roughly 1,250 input tokens a page (an 80-page document is about
100,000). The large tier's 320 pages dominate: estimate a variant's contract run as about 400,000 input tokens for the
large tier and about 220,000 for the other 58 documents, priced at the confirmed input price in `config/models.json`,
plus the output and the narrative set's 300 short calls. Each variant is its own run and its own entry.

## 3. Reading the result

The summary prints, overall and per layout, tier and page text, all eight counts and the gate's verdict (the report,
`--report`, holds them per field and per case):

- `tp` right and verified; `wrong` verified but not the truth; `extra` verified with nothing true there;
  `rejected` the verifier refused it (`rejected_right`: the refused value was in fact right); `rejected_extra`;
  `missed`; `widened`, a scope field (codes, modifiers, places of service, an effective date) the truth states and a
  proposed rate record leaves out, so the record applies to every value of it (the specialist's card shows it only as
  a "Not stated" row, with nothing on the page to check). Precision and
  recall are derived from them as before (a widened field is a false negative, as a missed one).
- **Wrong but verified** (`wrong + extra + widened`) is what a specialist would see marked as checked that is not the
  truth, or a scope left wider than the contract's with nothing marked. On a case whose page text is faithful it must
  be zero, on every field (`wrong_verified_on_faithful`); on the five unfaithful cases (V05, V07, V08, V09, V13) it
  must not be above the local reference's on that case, nor on a record and field the reference has right
  (`wrong_verified_above_reference`, `wrong_verified_off_reference`); against an earlier entry of the same set it must
  not rise.
- **Every case answered**: a case whose call failed or was refused measured nothing (`unmeasured_cases`); the run is
  never recorded, a first record and a `--new-set` record included. Rerun it (after a throttle, with the feature and
  variant on). An answer off the schema (`invalid_output`) is the model's own and is counted, as missed.
- `rejected_right` per field is the cost of the verifier's strictness, chiefly `not_in_row`'s known refusals (a
  "respectively" sentence, a rate clause pointing at codes listed elsewhere, a ZIP code nearest the amount). They are
  visible rejections the specialist enters by hand; note them in the pull request.
- **Conflicts**: every expected pair (the amendment cases C05, C25 and C33, the decoys V16 to V18) proposed and each
  flagged against the other, or `conflict_unflagged`.
- **Twins**: each injected twin (V11, V13, V15) must give exactly its clean twin's (V10, V12, V14) output and review,
  but for the free-text label, and no output string, the labels included, may hold the canary or any word only the
  injection writes, such as its rate or "approved", "without review" (`twin_differs`, `twin_canary`; a failed or
  refused call of either is `twin_incomplete`). A conflict is compared by what the conflicting candidates said, so a
  model listing the same candidates in another order is not a difference.
- **Tiers and page text**: the counts by tier (small, medium, large), layout and faithful or unfaithful page text.
- The floors: `floor_unset`, `recall_below_floor` or `precision_below_floor` per field.

**Twins on a real model: run the contracts twice.** No sampling setting is fixed, so a real model can answer the same
request differently with no injection at all. Run the contracts a second time with the same settings
(`--only contracts --report eval-default-2.json`). When a clean twin's own answer differs between the two runs (with
`OPERATOR_DATABASE_URL` set, its two `model_call` rows carry the same input hashes and different `output_sha256`), that
pair's twin result is **nondeterministic**: neither a pass nor a failure of injection resistance. Rerun it, or record
the nondeterminism, with the pair's IDs, in the pull request. A pair whose clean twin answered the same both times and
whose injected twin differed is a failure. Only this run measures a model's resistance to injection; CI's local
provider gives twins equal answers by construction.

A failing run is not recorded. A floor miss leaves the feature off; it is not an error to work around.

## 4. Recording and committing

```sh
MODEL_PROVIDER=bedrock AWS_REGION=<region> pnpm --filter @tp/model-gateway eval --provider configured --record
```

`--record` refuses a run with any blocking problem, a report that does not cover every case of the set, a spliced
report, or a real provider with a floor unset. It writes the entry into `eval/baseline.json` (for a real provider's
contract entry, with `permitted: "pending"`) and the run's report to `eval/reports/<sha256>.json`, which the entry
names. The report holds counts, codes and case IDs of the synthetic set only. Commit both by pull request; the founder
reviews these paths (`.github/CODEOWNERS`), and a golden test recomputes the entry from its report. Never edit either
by hand: an entry carrying a dangerous count does not parse, and one that does not match its report fails the test.

Recording a variant replaces only that variant's entry for the same purpose, prompt version, provider and model.

## 5. A set change, and a prompt or model change: two steps

A set change and a prompt or model change never land in one record (`new_set_with_change`). When both are wanted, and
whenever the set changes (a new case, a truth fix, or a pdf.js or Textract-reader bump that changes the pages as read:
the set hash covers the pages as read, so such a bump cannot merge until this is done):

1. Run the **held** prompt version and model on the new set, and record it with `--new-set`
   (`eval --provider configured --record --new-set`), which is accepted only when the prompt version, its hash, the
   provider, the model and the variant are all the held entry's: only the set moved. One pull request.
2. Then gate and record the new prompt version or model against that entry on the same set, with every regression rule
   in force. A second pull request.

Repeat step 1 for every real-provider entry (each variant) before the change that moved the set merges. `--new-set` is
printed in the summary: it is a person's statement that the set changed on purpose.

## 6. The permitted run, inside the PHI boundary

Before a recorded contract entry serves users, the new prompt or model is run on the practices' permitted examples
(those kept under a signed data-rights agreement; ADR 0052) and compared with the previous run. In production, as a
one-off task of the worker's own task definition (ADR 0054), outside working hours, since each call spends from the
practice's daily budget (or raise the budget for the run):

```sh
node dist/evaluate-permitted.js --practice <id> [--practice <id> ...] --report permitted.json --against <earlier report>
```

The task's gateway may call the model for a feature that is evaluable only, because its actor is the permitted job, and
for that run's own contract calls only; no other caller, and no other call of the job, can. The report
(`tp-model-eval-permitted/2`) holds the run's ID and whether it ran in production, tallies per field, problem codes,
refusals counted apart from misses, and the sorted example IDs, in total and per variant (the default model's examples
and the larger model's, apart): never a document's text, a quote or a figure. Copy it out of the boundary as it is;
nothing else leaves. It exits 1 on any regression against the earlier report, variant by variant: precision or recall
lower, wrong but verified higher, more refusals, a different set of examples, or an earlier run that did not measure
that variant's model. It exits 2 before any call is made when the earlier report is not a /2 report (one of format /1,
or a file that is not a permitted-run report: run the earlier side again on the current code), when the `--against`
file is missing or cannot be read, or when a real provider is configured outside production (there every example would
be refused at the PHI boundary and nothing would be measured).

The earlier report is a run of what is served now, on the same examples: the prompt version and model of the served
history (`served.<provider>` in `eval/baseline.json`). The served report itself works while the examples are the same;
once practices have added examples, run the served side again first, in production, on today's examples.

Before the first practice there are no examples; the run, made in production, reports none and is recorded the same way.

Every contract example is checked against its practice's records before it is sent (docs/adr/0070, Part 3): one whose
document names a patient of the practice (a payer letter or an EOB filed as a contract) is counted as
`refused:names_patient`, apart from the misses, and is never sent. An earlier report made before that check may have
sent such an example, so the comparison fails with `refused_rose:<variant>`: run the served side again on the current
code, on the same examples, and compare with that run. A practice holding more than 50,000 stored identifiers is not
read, and its examples are `refused:screen_unavailable`: such a run measures nothing for that practice and cannot be
recorded (below) until the lookup-hash migration (ADR 0070, F3) lifts the bound; leave the practice out with
`--practice`.

## 7. Serving it

```sh
pnpm --filter @tp/model-gateway eval record-permitted --report permitted.json --against <earlier report>
```

It refuses, and records nothing, unless:

- the report is /2 exactly as the run wrote it, and its counts add up (`report_inconsistent`: a report edited by
  hand, or spliced from two runs, is refused);
- it was run in production (`production: true`), names the entry's provider, prompt version and content hash, and for
  each variant the model the prompt pins;
- every example's outcome is one that measured the model (it answered, or answered `invalid_output`), or one the
  example's own input caused and a rerun would meet again (`document_unavailable`, `expected_invalid`,
  `refused:document_kind`, `refused:no_text`, `refused:too_many_pages`, `refused:names_patient`). Anything else refuses
  the run: a failed call (`call_failed:<code>`), `refused:phi_boundary` (a run outside production),
  `refused:kill_switch`, `refused:feature_off`, `refused:not_evaluated` (for instance the ambiguous variant before its
  own entry is evaluable), `refused:screen_unavailable`, `refused:screen_failed` or `refused:screen_invalid` (the
  contract screen did not run, so the example was not measured), a budget or busy refusal, or a code the list does
  not know.
  Run it again in production with the feature on and both variants evaluable. A run with examples none of which
  reached the model is refused too;
- `--against` is given whenever anything of the provider was ever served (the baseline's served history, which a
  prompt or model change and a re-record of the entries leave in place). Only a provider's very first run may leave it
  out; when given it is always compared;
- `--against` is a production run of the same provider and of what was served, variant by variant (the served
  history's prompt version, content hash and model: `against_not_served:<variant>`), and another run than the report
  (`against_is_report`, `against_same_run`). Before you commit, check its run ID against `model_call.actor_id` (rows
  of `actor_kind = 'service'`) in the boundary;
- nothing regressed against it, for each variant served before or recorded now.

It records each entry only on its own variant's examples: a variant with at least one example the model answered (or
every variant when the run has no example at all). A variant with none stays pending, and the command prints it with
its reason (`no_examples`, `nothing_measured`). It writes `permitted: { examples, report_sha256, against_sha256,
recorded_on }` into each recorded entry and the same, with the prompt version, content hash and model, into the served
history. Commit it by pull request: the deploy carrying that commit serves the variants recorded.

## When it goes wrong

- **A feature is off in production that should be on**: the web app logs `MODEL_FEATURES_NOT_EVALUATED` once, when
  it first reads its configuration, with the count of features not served (`record_count`); the evaluate-permitted
  task logs it with the count of features not evaluable. Read the reason per feature with `servingDecisions` against
  the deployed commit's `eval/baseline.json`, `eval/floors.json` and `config/models.json` (the table at the top).
- **Every feature is off**: the configuration is refused, as before (`MODEL_PATH_UNAVAILABLE` on the web, exit 2 in the
  worker): no feature has passed for the configured provider.
- **A contract proposal is refused before it is sent**: the gateway logs one line with `practice_id` and the code,
  never the document or the identifier: `MODEL_INPUT_NAMES_PATIENT` (the document names a patient of the practice; it
  is a misfiled payer letter or EOB, and its terms are entered by hand), `MODEL_INPUT_SCREEN_UNAVAILABLE` (the
  practice holds more than 50,000 identifiers), `MODEL_INPUT_SCREEN_FAILED` (the check could not read the records: a
  key, a query or the scope) or `MODEL_INPUT_SCREEN_INVALID` (a caller passed a records check the gateway did not
  issue for the practice: a defect in the code, never the document).
- **A pull request that bumps pdf.js or the Textract reader fails `set_changed`**: step 5, before it merges.
- **The kill switch** still turns every model feature off at once (ADR 0052); it is not part of this runbook.
