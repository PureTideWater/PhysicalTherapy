# Auth / tenant-isolation review: co-001/web-transaction-scope @ 766467cd (vs origin/claude/build-platform)

## S1 (should fix, close to blocker): a new services object per request resets the process-wide model call cap and the names_patient refusal cache
- apps/web/src/lib/server/services.ts:127-130: `signedInServices()` returns `Object.freeze({ ...kept, queue })`, a NEW object for every request (invoke.ts transacted: `services: signedInServices(services, sends.door())`).
- apps/web/src/lib/models/path.ts:110-119: `const limiters = new WeakMap<object, CallLimiter>()`; `modelLimiterOf(services)` is keyed on the services object's identity ("The process's cap on model calls in flight, one per set of services (a server builds one)").
- apps/web/src/lib/models/path.ts:122-131: `injected.get(services)` (assignModelPath) is keyed the same way.
- apps/web/src/lib/models/contract-proposals.ts:214, 220-239: `remembered = new WeakMap<object, …>`, keyed on services.
- apps/web/src/lib/routes/models.ts:56, 125, 154: the handlers pass their ctx `services` (now the per-request object) to proposeTerms / draftNarrativeWithModel / suggestChecklist, which call `gatewayFor(services, …)` (contract-proposals.ts:306, narrative-drafts.ts:51, evidence-checklist.ts:74).
- Scenario: a person (or several practices at once) fires concurrent model requests. Each request builds its own CallLimiter, so `tryAcquire` always sees 0 in flight. The perProcess and perPractice in-flight caps no longer apply to anything. The DB-side screen limits (rate_limit_take) still apply. The "remembered names_patient" refusal never hits, so a document that names a patient gets screened again on every click: decrypted, read, audited and counted against the limits. That is exactly what the cache exists to prevent. This does not reach another tenant. It is a regression in an AI-safety, cost and availability control that the change did not mean to make.
- Side effect, reasoned and not run: apps/web/src/lib/routes/models-routes.db.test.ts:176, 525, 993 call `assignModelPath(services, …)` on the base Services, so a handler's lookup through the per-request object misses and falls back to the env-configured path. Those route tests should fail or change behaviour. If they pass, check why.
- Fix direction: build the signed-in view once per Services (memoize in a WeakMap keyed on the base Services, with the queue door held apart), or key these caches on something stable that survives signedInServices (for example the base services or modelPool).

## S2 (should fix): the application login is still reachable outside the request's transaction through `modelPool`, and in createServices it IS the application pool
- services.ts:247: `modelPool: parts.modelPool ?? parts.pool`. Any Services built without a modelPool (every test that uses createServices without one, including transaction-scope.db.test.ts:44-55 `servicesWith`) hands the signed-in handler the very same pool object under another name. Production (services.ts:297) opens a separate pool on the same `config.databaseUrl`, which is the application login.
- `SignedInServices` (services.ts:124) omits only `pool | signIn | queue`. So `ctx.services.modelPool.connect()` gives any handler, or any helper it passes services to, a second connection on the application login. That connection is outside the request's transaction and practice scope, has no BOUNDED lock_timeout, and is not on the scope's client. Existing handlers already do this: contract-proposals.ts:174 (`await services.modelPool.connect()` for rate_limit_take) and :318 (practiceRecordsCheck opens its own job scope on modelPool). Both are documented under ADR 0055.
- What a handler gains: an unscoped connection. RLS fails closed on PHI tables without app.practice_ids. Another practice's rows would need `withPracticeScope(services.modelPool, { practiceIds:[other] })` to pass the DB's own membership check, which I did not re-verify in this review (no migration changes in this diff: `git diff --stat … packages/db/functions packages/db/migrations` is empty). So I found no cross-tenant read. The finding is that the headline claim, "a signed-in handler can no longer take a second connection from the application pool", holds for the property named `pool` and not for the login. The test at transaction-scope.db.test.ts:333-357 checks `'pool' in services === false` but never checks `modelPool !== pool`, and in that test the two are identical.
- Fix direction: either state the claim narrowly (the request pool only; modelPool is the gateway's, by ADR 0055), or give handlers a narrowed gateway handle instead of a raw ScopePool. In either case, make createServices refuse `modelPool === pool`, or add the check to the test.

## S3 (note): CommitOutcomeUnknownError keeps the pg error as `cause` and is rethrown to the framework
- packages/db/src/authz/scope.ts (new class `CommitOutcomeUnknownError`, `super(…, { cause })`), and invoke.ts `transacted` → `refuse(error)` → refusal() falls through to `throw error` (invoke.ts:452).
- The wrapper's own lines are clean: COMMIT_NOT_APPLIED and COMMIT_OUTCOME_UNKNOWN log `{ error_code, request_id }` only. QUEUE_COMMIT_FAILED logs `{error_code, request_id}`. JOB_NOT_QUEUED_AFTER_COMMIT logs `{error_code, job_type, request_id}`. All of these fields are in packages/observability/src/fields.ts. The messages carry no identifier, statement or URL.
- Reasoned: the rethrown error reaches Next.js's default error logging, which prints the stack and Node's `cause` chain. The cause is the pg error of a failed COMMIT ("Connection terminated unexpectedly", or a FATAL such as admin shutdown). pg does not attach query text or the connection string to these errors. This is the same exposure every other unhandled pg error in a handler already had, so it is not new. I did not find an onRequestError/instrumentation hook that would log `cause` as structured fields.

## S4 (note): an unknown commit outcome commits the request's jobs
- request-sends.ts settle(): `CommitOutcomeUnknownError` → `held.commit()`. The jobs were enqueued by a handler that had already passed the in-transaction permission check for that practice, so a job cannot target a practice the actor cannot reach. If the request did not in fact commit, the job finds nothing. This is a deliberate, documented trade-off and not an isolation hole.

## What I tried and could not break
- Order and content of the three wrappers (git diff of invoke.ts). Guards, session/MFA checks and the early `refused` return are untouched and come before `transacted`. Inside the transaction the order is the same as before: gates → not-found (practice: `scope.access`; org: `organizationRoles` empty) → permission → RUN_STARTING_ROUTES (practice) → platformRoles → run() (request-key claim, handler, audit event, shell). BOUNDED is still passed: as withActor's last argument (actor, org routes) and via `...BOUNDED` in withPracticeScope's options (practice route), as before. Refusal mapping is the same function with the same arguments: 55P03 → busy with `{error_code:'LOCK_TIMEOUT', request_id}`, and the forbidden shell is still its own BOUNDED read. After-commit work still runs only on success, and now also only after the queue settles.
- Jobs on refusal. Every refusal that throws (NotFound, PermissionDenied, Suspended, Busy, 55P03, Terms, Maintenance, Input) goes through catch → `settle(error)` → rollback. A duplicate request key returns before handle(), so nothing is pending. `hold()` is called only after run() returns, inside the transaction, so a failed hold rolls the request back (PgBossQueue.hold rolls back its own transaction on failure). A handler that swallowed a statement error now gets TransactionNotCommittedError, and its jobs roll back too, where before they had been sent. This is stricter than the old code. A handler that *returns* a non-ok outcome without throwing commits, with its jobs. Under the old code those jobs were sent immediately, so that is no weaker.
- The queue door: `door()` is a frozen object with only `enqueue`, and `hold`/`settle` are not reachable from it. enqueue after the request ended throws. After commit it sends directly, which is correct for AfterCommit.
- `services()` process accessor and helpers typed with full `Services`: the diff retypes helpers to `SignedInServices`/Picks (billing.ts:50 Picks billingPool and billing). I found no signed-in handler that imports the process-wide accessor, but I did not grep all of apps/web for `services()` call sites, within the budget. billingPool and esignPool are other logins, kept on purpose (ADR 0055), and their use comes after the permission check (onboarding.ts:183 esignPool predates this change).

## Verified vs reasoned
- Verified by reading code: S1 (the WeakMap keys, the per-request object, the handlers passing ctx services), S2 (createServices fallback, the test's servicesWith, the existing modelPool.connect calls), all log field sets, wrapper order.
- Reasoned and not executed: the models-routes.db.test.ts fallout under S1, Next.js's logging of `cause` under S3, and the DB-side membership check on a scope opened through modelPool under S2.
