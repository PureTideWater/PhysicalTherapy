-- While a removal of an account's keys is requested, that account changes the status and the hardware-key rule of no
-- other account: as a platform administrator it could otherwise disable the requester, which voids the request
-- (hardware_key_removal_requester_left), or any administrator who could confirm it. Its own row it may still change,
-- and once the request is decided (confirmed, cancelled or marked expired) the rules that stood before decide alone.
-- It takes no lock. By name it fires after user_guarded_columns and before user_updated_at; the order changes no
-- outcome, since only a platform administrator reaches another account's row and user_guarded_columns passes one.
CREATE FUNCTION user_removal_target_holds() RETURNS trigger
LANGUAGE plpgsql VOLATILE SECURITY DEFINER SET search_path = pg_catalog, public, pg_temp AS $$
BEGIN
  IF app_actor_id() IS NOT NULL
     AND OLD.id <> app_actor_id()
     AND EXISTS (SELECT 1 FROM hardware_key_removal r WHERE r.user_id = app_actor_id() AND r.state = 'requested') THEN
    RAISE EXCEPTION 'an account whose key removal is requested changes no other account''s status or hardware-key rule until the request is decided'
      USING ERRCODE = 'check_violation', CONSTRAINT = 'hardware_key_removal_target_acts';
  END IF;
  RETURN NEW;
END;
$$;
REVOKE ALL ON FUNCTION user_removal_target_holds() FROM PUBLIC;
CREATE TRIGGER user_removal_target_holds BEFORE UPDATE ON "user" FOR EACH ROW
  WHEN (NEW.status IS DISTINCT FROM OLD.status OR NEW.hardware_key_required IS DISTINCT FROM OLD.hardware_key_required)
  EXECUTE FUNCTION user_removal_target_holds();

-- END SQL
--
-- CONVENTIONS FOLLOWED (as membership_removal_target_holds, same section): plpgsql VOLATILE SECURITY DEFINER (it must
-- be DEFINER: tp_app holds nothing on hardware_key_removal, which is FORCE RLS and revoked), SET search_path =
-- pg_catalog, public, pg_temp, owner tp_owner, EXECUTE revoked from PUBLIC and granted to no one (forNone), RAISE ...
-- USING ERRCODE = 'check_violation' (23514), CONSTRAINT = 'hardware_key_removal_target_acts'. Same constraint name as
-- the membership trigger, by the ruling: one name for "the target of a requested removal acts".
-- The WHEN clause compares values, so an UPDATE that names status but does not change it is not refused, and an UPDATE
-- of other columns (sign_in_not_before by the confirmation and by membership_end_marks_account, locked_at, settings,
-- email) never enters the function. app_actor_id() IS NULL (the owner, the platform jobs) is never bound.
--
-- LOCKS. The trigger takes none: no FOR UPDATE/SHARE, no LOCK TABLE, no advisory lock; its EXISTS is a plain read of
-- hardware_key_removal under the statement's READ COMMITTED snapshot. The only lock in play is the one the UPDATE
-- itself already holds on the "user" row being changed (taken before any BEFORE ROW trigger runs). The confirmation,
-- the cancel and the request take the ACCOUNT's (the target's) "user" row FOR NO KEY UPDATE and then the removal row
-- FOR UPDATE (docs/adr/0093 D2's order); the confirmation reads the requester through account_removes_keys() without
-- a lock. The bound actor's statement holds another account's row and waits on nothing the trigger adds, so the
-- trigger adds no edge to any wait graph and cannot deadlock with them. (A plain row-lock wait is still possible as
-- before: the target's UPDATE of B's row waits if B's row is locked, e.g. B is itself the account of a removal being
-- confirmed; that wait exists today without the trigger.)
-- RESIDUAL, by taking no lock (the same as membership_removal_target_holds): a request not yet COMMITTED when the
-- target's UPDATE statement takes its snapshot does not bind it. The target cannot know of an uncommitted request, and
-- a platform administrator disabling another before any request stands is the standing rule, so this was left; it
-- would be closed only by the trigger taking the actor's own "user" row (the request holds it), at the price of a
-- second row lock in the other order (B's row, then T's own), which CAN deadlock against two accounts acting on each
-- other. Not proposed.
