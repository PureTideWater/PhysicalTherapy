## Findings

1. should-fix. ADR 0087 dated note ("The match lookups have no such state: without `reversed_at IS NULL` in the query only the primary key fits") and the worker test's block comment ("The match lookups hold in every state: only the primary key fits them") are false. In the analyzed-while-empty state, which the ADR's own table lists (R's seed), both installed match reads plan `Seq Scan on ledger_match m` (copy of tp_pr2_base + migration, `ANALYZE ledger_match` on the empty table, EXPLAIN GENERIC_PLAN as tp_app). Smallest fix: say "on a never-analyzed ledger_match only the primary key fits; analyzed while empty, both reads (old bodies too, not measured here) plan a sequential scan", and add that state to the table's ledger_entry_rules side. Do not touch the bodies.
2. note. Test block comment: "the planner learns nothing of the rows the pass then writes" overstates the mechanism. With reltuples -1 the planner reads the relation's current size at each planning (the plan flips with heap pages: 3 -> by_line, 4 -> by_date on the copy). What holds the pass's first plan is the plan cache, not ignorance of size. Smallest fix: "...and the plan it keeps does not change as the pass writes; the pass's own rows give no statistics".
3. note. "a few hundred" (migration Known limit, test comment) and "about 200" (ADR row 2) put the lower bound of the by_date state too high. On the copy it starts at 160 entries (4 heap pages), and the boundary depends on pages, not entries. Smallest fix: "from about 150 synthetic entries (4 pages)".
4. note. The worker test's beforeAll comment still says "so the last group plans on a ledger with rows and no statistics". The group is now the first, and it starts empty. Smallest fix: "the first group".
